# 捕账（AppMessageCapture）系统全面扫描评估报告

> 扫描日期：2026-09-14　｜　代码版本：main 分支 d960c4b（versionName 2.2.7 / versionCode 3）
> 扫描方式：全量源码通读（112 个 Kotlin 文件 / 约 2.55 万行）+ 构建/测试实跑验证 + Manifest、ProGuard、Gradle、schema、脚本、文档逐项核对
> 健康度基线：`gradlew :app:compileDebugKotlin` 通过；`gradlew :app:testDebugUnitTest` **147 个测试全部通过**（0 失败 0 错误）

## 一、总体结论

项目整体工程质量**明显高于同类个人项目水平**：解析逻辑全部抽成可单测的纯函数、入库走统一管线 + 互斥锁、余额联动全部收口在 `AccountRepository` 事务内、迁移链完整（v2→v17）、147 个单测真实覆盖边界场景（真机 dump 文本、60 秒去重边界、闰年月末钳制等）。

但扫描仍发现 **9 个高危问题**（多数为「功能静默失效」类，用户无感知地丢数据/丢提醒）、约 30 个中危问题、60+ 低危与改进项。最需要优先处理的是：

1. **Release 包生日备份导入会静默坏数据**（ProGuard 漏 keep Gson DTO）；
2. **生日闹钟链会静默断裂**（触发时间过期即跳过 + 农历年换算错误，两条路径都导致「生日到了却没提醒」）；
3. **Android 14 默认无 SCHEDULE_EXACT_ALARM 权限时生日提醒全部被丢弃**（`setAlarmClock` 本不需要该权限，前置检查把整个调度拦死了）；
4. **编辑账单时 4 个写库操作并发执行**，平台余额可能算错（记账 App 的资损级问题）；
5. **Room v1→v2 迁移缺失**，v1 设备升级直接崩溃。

以下分模块给出全部发现，每条含位置、证据、影响与修复建议。

## 二、高危问题（P0，建议立即修复）

### H-1. ProGuard 漏 keep 生日备份 DTO，Release 包导入备份会静默得到空/坏数据
- **位置**：`app/proguard-rules.pro:5-10` vs `birthday/utils/BackupManager.kt:83-84,157`
- **证据**：keep 规则只覆盖 `com.aifactory.appmessagecapture.data.**` 和 `birthday.data.**`，而导入反序列化用的是 `birthday.utils.BackupManager$BirthdayBackupItem`（`TypeToken<List<BirthdayBackupItem>>`）。项目开启了 R8 fullMode（AGP 8.x 默认），字段名会被重命名，导出的 JSON key（`name`/`isLunar`…）与运行时字段对不上；同时缺少 Gson 标准规则（`-keepattributes Signature,*Annotation*`），匿名 `TypeToken` 的泛型 Signature 被剥离后会退化成 `List<LinkedTreeMap>` → ClassCastException。
- **影响**：仅影响 release 包（debug 未混淆）——用户导出的生日备份在 release 版导入时**静默**变成空对象/直接抛异常，且极难排查。
- **修复**：
  ```
  -keep class com.aifactory.appmessagecapture.birthday.utils.BackupManager$BirthdayBackupItem { *; }
  -keepattributes Signature, *Annotation*
  ```
  并把「导出→导入」回环加进 release 冒烟清单（顺带把 DTO 挪进 `birthday.data` 包更稳）。账单备份走自研 xlsx（`MiniXlsx`），不经 Gson，无此风险。

### H-2. 生日闹钟「触发时间已过即跳过」，年度闹钟链会静默断裂
- **位置**：`birthday/service/BirthdayAlarmScheduler.kt:68-76`
- **证据**：
  ```kotlin
  val triggerMillis = calculateTriggerTime(birthday)
  if (triggerMillis <= System.currentTimeMillis()) { ...; return }
  ```
- **影响**：生日当天关机错过 09:00 → 开机 → BootReceiver → `rescheduleAll` → 触发时间已过 → 跳过且**不给下一年注册** → 此后一年无提醒。覆盖安装（系统会清除所有精确闹钟）后同样断链，而 Manifest 没有监听 `MY_PACKAGE_REPLACED` 的恢复路径。
- **修复**：过期时改为调 `scheduleForNextOccurrence(context, birthday)` 落到下一次发生；`scheduleForNextOccurrence` 内部也应基于持久化的「上次触发年份」推进，而不是重新 `calculate`（避免连锁多跳一年）。补 `MY_PACKAGE_REPLACED` 与 `TIME_SET/TIMEZONE_CHANGED` 监听。

### H-3. 农历生日用公历年当农历年，农历 10~12 月生日在元旦~春节窗口会被跳过一整年
- **位置**：`birthday/logic/DateCalculator.kt:219-235`（`findNextLunarBirthday`）
- **证据**：`LunarCalendarAdapter.lunarToSolar(currentYear, month, day)` 中 `currentYear` 是今天的**公历**年份，却被当作**农历**年份。反例：今天 2027-01-10（农历仍是丙午年），生日为农历 12-15 → `lunarToSolar(2027,12,15)` ≈ 2028-01，被判为「未来」直接返回；而真正的下一次是农历 2026-12-15 ≈ 2027-01-22（12 天后）——眼前的生日被跳过，提醒晚一整年。KDoc（154-157 行）显示这是有意为之的设计，但边界是错的。
- **影响**：每年 1/1~春节之间，凡农历十月以后的生日，下次提醒日计算全部错误（提前一年）。`scheduleForNextOccurrence` 第一步就调用该函数，闹钟同样受影响。
- **修复**：先 `Solar(today).lunar` 取真实当前农历年 Y，再分别算 `lunarToSolar(Y, …)` 与 `lunarToSolar(Y+1, …)`，取第一个不早于今天的日期。可用现有注入 `baseDate` 的测试框架先补反例用例再修。

### H-4. Android 12+ 无精确闹钟权限时，生日提醒调度被整体拦截——但实际用的 `setAlarmClock` 根本不需要该权限
- **位置**：`BirthdayAlarmScheduler.kt:60-66`（前置 return）vs `:104`（`alarmManager.setAlarmClock(...)`）
- **证据**：`setAlarmClock` 是系统闹钟语义 API，**豁免** `SCHEDULE_EXACT_ALARM`；但代码在进入调度前先检查 `canScheduleExactAlarms()`，Android 14（targetSdk 33+）该权限默认拒绝 → 默认状态下所有生日闹钟被静默丢弃，仅有一个列表页 banner 提示。
- **修复**：走 `setAlarmClock` 路径时删掉该前置检查；若保留 `setExact` 分支再检查；另外对 15 天内的生日用 `setAndAllowWhileIdle` 做兜底，防用户事后撤销权限时系统清掉已设闹钟。

### H-5. 编辑账单时 4 个写库操作并发执行，平台余额可能算错
- **位置**：`ui/BillScreen.kt:926-935` + `ui/BillViewModel.kt:299-334`
- **证据**：
  ```kotlin
  if (titleChanged) viewModel.updateTitle(bill.id, editTitle.trim())
  if (amountChanged) { ... viewModel.updateAmount(bill.id, it) }
  if (categoryChanged) viewModel.updateCategory(bill.id, editCategory)
  if (platformChanged) viewModel.reconcileBill(bill.id, editPlatformId)
  ```
  四个方法各自 `viewModelScope.launch(Dispatchers.IO)` 并发跑。用户同时改金额+平台时，`updateAmount`（按旧平台±差值）与 `reconcileBill`（回滚旧平台+计入新平台）没有先后保证，两个事务交错后**平台余额与真实金额不一致**。
- **修复**：ViewModel 提供单一 `updateBill(bill, changedFields)` 入口，在一个协程内按「先改金额、再对账」的固定顺序调用 Repository（或合并为一个 Repository 事务方法）。

### H-6. Room 缺 v1→v2 迁移且无破坏性兜底，v1 设备升级直接崩溃
- **位置**：`data/AppDatabase.kt:405`（迁移链从 `MIGRATION_2_3` 开始）、`:398-411`（未配 `fallbackToDestructiveMigration`）
- **影响**：若线上仍存在数据库版本 1 的设备（最早发布的安装包），升级后首次打开抛 `IllegalStateException: A migration from 1 to 17 was required but not found` 崩溃。`优化建议方案.md` 六.4 早已指出，至今未处理。
- **修复**：确认 v1 是否真实发布过；发布过则补 `MIGRATION_1_2`（参照 schema/8.json 反推），没发布过则在文档标注「v1 从未发布」闭合该风险。

### H-7. 报表聚合计算全部跑在主线程
- **位置**：`ui/report/ReportViewModel.kt:52-63, 137-209`
- **证据**：`combine(...).flatMapLatest { billDao.getBillsSince(...).mapLatest { buildUiState(it) } }.collect{}` 全链无 `flowOn(Dispatchers.Default)`；`buildUiState` 内 4 个 calculate* 对「年报=5 年」的全部账单做多次 filter+groupBy+sumOf，每次切换周期/新账单入库都重算。
- **修复**：链上加 `.flowOn(Dispatchers.Default)`；`getBillsSince` 只取当前周期所需时间窗；bar/trend 可拆独立查询。

### H-8. 全屏实时 RenderEffect 模糊 + 31 个无限动画，整机 GPU 常态满载
- **位置**：`ui/components/LiquidGlass.kt:45-64`、`ui/components/SoftComponents.kt:569-634`、`MainActivity.kt:166-170`
- **证据**：`GlassBackdropRoot` 用 `drawWithContent` 把整棵子树（含列表）每帧录到离屏层再做 28dp `BlurEffect` 全屏模糊 + 内容再画一遍 = **每帧两次全屏绘制 + 一次全屏模糊**；底层 `AmbientBackground` 同时跑 9 个光斑 ×2 + 9 个颜色 + 4 段底色 = 31 个 `infiniteRepeatable` 永不停。
- **影响**：空闲时也持续全屏重绘+模糊，中低端机（尤其无硬件模糊加速的 API 31-33）掉帧、发热、耗电。
- **修复**：① 提供设置开关/低配自动降级；② 模糊只作用于背景层（静态低分辨率快照，滚动时才更新），不要包内容层；③ 光斑砍到 3-4 个或页面不可见时暂停。

### H-9. 导出 JSON/CSV 无异常处理，IO 失败直接崩溃；导出文件滞留 cacheDir
- **位置**：`ui/NotificationViewModel.kt:290-326`
- **证据**：`viewModelScope.launch(Dispatchers.IO) { ... file.writeText(...) }` 未 try/catch，磁盘满/权限异常直接崩进程，UI 无感知（`onComplete` 只处理 null 失败路径）。
- **修复**：`runCatching` 包裹，失败回调 `onComplete(null)` 或走 `_backupMessage` 通道提示；分享完成后删除临时文件。
