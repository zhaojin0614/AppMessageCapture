# 实施计划：消息保留期、日均计算修正、平台账户管理

本计划覆盖用户的三个需求，分为三个独立功能模块。数据库从 v11 升级到 v12，一次性迁移。

---

## 模块一：消息只保留最近一个月（自动删除超期消息）

### 目标
通知消息（`notifications` 表）只保留最近 30 天，超期自动删除，缓解存储压力。

### 实现
1. **`NotificationDao.kt`** — 新增方法：
   - `@Query("DELETE FROM notifications WHERE timestamp < :before") suspend fun deleteOlderThan(before: Long): Int`
   - `@Query("SELECT COUNT(*) FROM notifications WHERE timestamp < :before") suspend fun countOlderThan(before: Long): Int`（可选，用于日志）

2. **新增 `worker/NotificationCleanupWorker.kt`** — 仿照 `RecurringBillWorker` 模式：
   - `CoroutineWorker`，每日执行一次（`PeriodicWorkRequestBuilder`，`ExistingPeriodicWorkPolicy.KEEP`）
   - `doWork()` 中计算 `threshold = startOfDay(now) - 30天`，调用 `notificationDao.deleteOlderThan(threshold)`，记录日志（复用 `BirthdayLog`）
   - `schedule(context)` 静态方法，在 `AppMessageCaptureApplication.onCreate()` 中调用（与 `RecurringBillWorker.schedule` 并列）

3. **`AppMessageCaptureApplication.kt`** — `onCreate()` 增加 `NotificationCleanupWorker.schedule(this)`

### 注意
- 账单（`bills`）不受此清理影响，只清理通知消息。
- 30 天按自然日计算（`LocalDate.now().minusDays(30)` 的当天 0 点）。

## 模块二：修正报表日均/月均计算逻辑

### 目标
当前 `dailyAvg` 按完整周期天数计算（周=7天、月=整月天数、年=12个月），导致"本周日均"把未发生的天数也算进分母。改为按**当前周期内已过去的实际天数**计算。

### 问题定位
`ReportViewModel.loadData()` 第 116-125 行：
```kotlin
val daysInPeriod = when (type) {
    PeriodType.WEEK -> 7L
    PeriodType.MONTH -> ChronoUnit.DAYS.between(currentRange.start, currentRange.end) + 1
    PeriodType.YEAR -> 12L
}.coerceAtLeast(1)
val dailyAvg = when (type) {
    PeriodType.YEAR -> selectedCurrentTotal / 12.0
    else -> selectedCurrentTotal / daysInPeriod
}
```
无论查看的是当前周期还是历史周期，分母都是完整周期长度。查看"本周"（今天是周二）时分母=7，但实际只有 2 天有数据，日均被压低。

### 修复方案
分母改为**该周期内已过去的实际天数**：
- **查看当前/未来周期**（offset >= 0）：分母 = 从周期起点到今天的天数（含今天），最小为 1。若今天在周期起点之前（未来周期，如本周一时查看"本周"但周一算第1天），则取 1。
- **查看历史周期**（offset < 0）：分母 = 完整周期天数（历史周期已完整结束，按整周期算才合理）。

具体修改 `ReportViewModel.loadData()`：
```kotlin
val today = LocalDate.now()
val elapsedDays = when {
    // 历史周期：按完整周期算
    offset < 0 -> when (type) {
        PeriodType.WEEK -> 7L
        PeriodType.MONTH -> ChronoUnit.DAYS.between(currentRange.start, currentRange.end) + 1
        PeriodType.YEAR -> 12L
    }
    // 当前/未来周期：按已过去天数算（含今天），最少1天
    else -> {
        val periodStart = currentRange.start
        val periodEnd = currentRange.end
        if (today.isBefore(periodStart)) {
            1L  // 周期尚未开始
        } else if (today.isAfter(periodEnd)) {
            // 周期已结束但 offset>=0（边界情况），按完整周期
            when (type) {
                PeriodType.WEEK -> 7L
                PeriodType.MONTH -> ChronoUnit.DAYS.between(currentRange.start, currentRange.end) + 1
                PeriodType.YEAR -> 12L
            }
        } else {
            ChronoUnit.DAYS.between(periodStart, today) + 1  // 含今天
        }
    }
}.coerceAtLeast(1)

val dailyAvg = selectedCurrentTotal / elapsedDays
```
- 周视图：周二查看本周 → elapsedDays = 2，日均 = 本周支出/2。
- 月视图：当月15号查看 → elapsedDays = 15。
- 年视图：月均 → 同理按已过月数（offset>=0 时 = `today.monthValue`，offset<0 时 = 12）。

UI 标签（`ReportScreen.kt` 第 395-401 行的 "日均/月均"）保持不变，仅数值计算修正。

### 测试
新增/补充 `ReportViewModel` 的单元测试（如项目无现成报表测试则新建 `ReportAvgTest.kt`），覆盖：当前周周二、历史完整周、当前月中、历史月、当前年、历史年等场景的日均分母。

## 模块三：平台账户总金额管理（核心功能）

### 目标
新增"平台账户"管理：记录各平台余额，可增删改查；记账界面下拉显示总金额；账单可关联扣款平台；未关联的账单标记"未对账"，可后续分配。

### 采用的决策（推荐方案，用户未明确反对）
1. **收入也关联平台**：收入账单可选存入平台，收入时该平台余额+金额、总金额+金额。对称设计，余额始终准确。
2. **自动记账账单默认标记"未对账"**：自动识别的账单（来自通知/周期账单）默认不分配平台，只显示在总金额无关的状态。用户后续手动分配平台，分配时从对应平台扣款。
3. **对账方式**：账单列表中未对账账单显示警示标记（橙色徽章"待对账"），点击账单弹出平台选择框分配。无需单独对账页面。
4. **余额自动回滚**：删除已关联平台的账单时自动把金额加回平台；修改账单金额/平台时自动调整差额。

### 数据层

   ```kotlin
       val name: String,           // 平台名称，如"微信钱包"、"支付宝"
       val balance: Double,        // 当前余额
       val icon: String? = null,   // 预留图标标识（暂用名称首字母）
       val sortOrder: Int = 0,     // 排序
       val createdAt: Long = System.currentTimeMillis(),
       val updatedAt: Long = System.currentTimeMillis()
   )
   ```

3. **`BillEntity.kt` 扩展** — 新增字段（数据库迁移）：

   ```kotlin
   val reconciled: Boolean = true         // 是否已对账（已分配平台）。为兼容旧数据默认true
   ```

   > 说明：`platformAccountId` 非空即已对账；为空且 `reconciled=false` 即"待对账"。两个字段冗余但便于查询和展示。也可只用 `platformAccountId`（null=待对账），简化为单字段——**实施时采用单字段方案**：`platformAccountId: Long? = null`，null 即未对账，非空即已对账。更简洁。

### 数据一致性要点
- 所有账单-平台联动必须走 `AccountRepository` 的 `@Transaction` 方法，禁止直接 `billDao.insert` + `platformDao.adjustBalance` 分步调用，避免中途失败导致余额不一致。
- `MessageCaptureService` 中现有的 `dao.insert(bill)` 路径：自动账单本身未对账，不涉及平台扣款，保持现状即可（插入后用户手动对账时才扣款）。

## 风险与备注
- **数据库迁移**：v11→v12 需在真机升级时验证。`ALTER TABLE bills ADD COLUMN platformAccountId INTEGER` 对旧账单默认 null（未对账），符合预期——旧账单视为未对账，用户可选择性分配。这点需在 UI 上让旧账单也显示"待对账"标记，可能量大，后续可考虑批量忽略。**实施时默认旧账单 `reconciled=true`（即不标记待对账）以避免历史账单全标橙**——但单字段方案下无法区分"旧数据未对账"和"新账单待对账"。**最终决策**：迁移时给旧账单的 `platformAccountId` 仍为 null，但在 `BillCard` 中只对"迁移后新产生的且 timestamp 在迁移时间点之后"的账单显示"待对账"徽章过于复杂。简化：**所有 platformAccountId=null 的账单都显示"待对账"徽章**，用户可批量点击忽略或分配。这是可接受的，因为用户主动管理平台后会逐步消化。

- **余额初始值**：用户首次进入平台管理需手动录入各平台当前余额，应用无法自动获取真实余额。

- 编译验证使用 `./gradlew assembleDebug`（Windows 下 `gradlew.bat`）。
